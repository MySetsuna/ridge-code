# Iteration 47 报告 —— 根因修复:LLM 调用无超时致真实任务永久冻结

> 触发 = 用户报「真实任务一直执行不完」;非 NLM 循环,是直接 bug 报告 + 代码核实定位。

## 根因(证据链)

- `ReqwestClient`(承载全部 LLM HTTP 调用)= `reqwest::Client::new()`,**零超时**;流式 `resp.chunk().await` 无 idle 超时。唯一带超时的是 web-search 模块(15s),**非 LLM 路径**。
- `RunConfig.max_supersteps=100` 与 agent `MAX_STEPS=30` 都在**超步之间**检查——**单个 LLM 调用卡在超步内时,`await` 永不返回,这俩护栏拦不住**。
- `~/.ridge/audit.log` 显示任务**时而完成**(steps 1~13,tokens 达 207k)——**间歇性冻结**,正是「GLM 端点/代理偶发流式卡住(慢 / SSE 不发 `[DONE]` / 连接不关)→ 该调用永久 hang → 任务冻死」的特征,非死循环、非 budget。

## 修复

`crates/provider` `ReqwestClient`:
- `connect_timeout(30s)`(防连接挂死)。
- **非流式** `post_json`/`get_json`:逐调用 `.timeout(RIDGE_HTTP_TIMEOUT|180s)`(整请求超时)。
- **流式** `post_json_stream`:`tokio::time::timeout` 包 `send`(响应头等待)与**每次 `chunk`(逐块 idle 超时)** —— 流中途卡住 → 中止报错(不冻结);正常慢流每块刷新计时,**不误杀**。
- 超时秒数 env `RIDGE_HTTP_TIMEOUT` 可调(默认 180),给慢端点留活口。

## 测试状态

`cargo test --workspace && cargo fmt --all --check && cargo clippy --workspace --all-targets -- -D warnings` 全 **exit 0**;provider 33 / 全仓不变。
- **不加计时型单测**:超时触发是时序/环境行为,与 loop「确定性纯函数验收、禁计时/PTY 断言」铁律相悖;既有替身 HttpClient 测试不走真实客户端故不受影响。修复由「编译 + 既有全绿 + 真实任务不再冻结」验证 —— 诚实边界:活验证需用户实跑。

## 影响面

超时是纯**叠加**护栏:happy-path(端点正常响应)行为零变化;仅在**端点卡住**时把「永久冻结」变成「超时报错 → 任务失败可重试」。所有 provider(经 `ReqwestClient`)同获保护。

## 开放 / 后续

- 用户报的其余 TUI 问题(底部多余状态条 / 下方状态条换行 / Shift+Enter 换行失效 / 光标卡首行)本轮**延后**(用户明确先修任务冻结)。
- 若默认 180s 对某端点仍太紧,`RIDGE_HTTP_TIMEOUT` 调大;或后续升为 config 字段。
